## 2. 指标解释

### 2.1 IOPS（Input/Output Operations Per Second）

**定义**：每秒完成的操作次数。对于查找基准，一次操作 = 一次 `GetValue(key)` 调用；
对于缓存/工作集基准，一次操作 = 一次 `FetchPage(page_id)` 调用。

**物理意义**：IOPS 衡量系统在单位时间内能处理的请求量，是数据库和存储系统的核心性能指标。
在 Larger-than-Memory 场景中，IOPS 受以下因素影响：

- **缓存命中率**：命中时仅需内存访问（纳秒级），未命中需磁盘读取（微秒级）
- **树高度**：每次操作需要遍历从根到叶子的路径，每层一次 FetchPage
- **数据局部性**：顺序访问利用缓存，随机访问破坏缓存

### 2.2 WAF（Write Amplification Factor）

**定义**：WAF = 物理写入字节数 / 逻辑更新字节数

**物理意义**：每次逻辑更新（修改几个字节）最终导致多少物理 I/O（写整页 4KB）。
WAF 越高，存储设备的寿命损耗越大（尤其是 SSD），有效带宽浪费越多。

### 2.3 吞吐量 vs 延迟

本报告以 IOPS（吞吐量）为主要指标。吞吐量和延迟的关系为：

```
延迟 (ms) = 1000 / IOPS (近似，假设负载为连续独立请求)
```

例如：
- 100 万 IOPS → 每次操作 ~0.001 ms（1 μs）
- 1 万 IOPS → 每次操作 ~0.1 ms（100 μs）

## 3. 控制变量分析框架

每个基准测试都遵循"控制变量法"的设计思路：

| 测试 | 自变量（变化） | 因变量（测量） | 控制变量（固定） |
|------|--------------|--------------|----------------|
| 纯查找 | 数据规模 (1K~1M) | Lookup_IOPS | Pool=64, 随机 key, 扇出=250 |
| 缓存压力 | Pool 大小 (4~256) | Throughput_IOPS | 工作集=200 页, 5 万次访问 |
| 树高演化 | 数据规模 (100~1M) | Tree_Height | 扇出=250, 有序插入 |
| 顺序 vs 随机 | 访问模式 (seq/rand), 数据规模 | IOPS | Pool=32, 相同数据集 |
| 写放大 | 更新粒度 (8B~2KB) | WAF | Pool=4, 每次修改后强制刷出 |
| 混合负载 | 数据规模 (10K~1M) | Mixed_IOPS | Pool=64, 30%插入+50%查找+20%更新 |
| 工作集压力 | 工作集大小 (5~1000 页) | Throughput_IOPS | Pool=10, 1 万次轮询访问 |

这种设计保证了每个测试能独立评估某个因素的影响，且多个测试的结果可以交叉验证。

### 4.6 多层级分析

#### 页面级分析

每次随机查找需要从根到叶子逐层加载页面。当数据规模为：

- **1K（~4 页叶子）**：树高=1，所有页面（根=叶子）常驻缓存，查找退化为纯内存二分查找
- **10K（~40 页叶子）**：树高=2，根节点常驻缓存，叶子节点开始被淘汰
- **100K（~400 页叶子）**：树高=2，叶子约 400 页 > 池 64 页 → 频繁淘汰
- **500K（~2000 页叶子）**：树高=3，增加一层内部节点，叶子 2000 页 → 更多 I/O
- **1M（~4000 页叶子）**：树高=3，叶子 4000 页 → 缓存命中率进一步下降

#### 树级别分析

| Scale | 树高 | 每次查找的 FetchPage 次数 | 潜在 I/O 次数 |
|:-----:|:----:|:------------------------:|:-------------:|
| 1,000 | 1 | 1 | 0~1（根即叶子） |
| 10,000 | 2 | 2 | 0~2（根缓存，叶子不一定） |
| 100,000 | 2 | 2 | 0~2 |
| 500,000 | 3 | 3 | 1~3（内部节点可能被淘汰） |
| 1,000,000 | 3 | 3 | 1~3 |

树高从 1 增加到 3，每次操作的页访问次数从 1 增加到 3，但 IOPS 从 ~100 万降至 ~1 万，
下降约 100 倍。这说明树高增加只能解释 3 倍差异（从 1 次到 3 次 FetchPage），
**主要瓶颈在于缓存命中率**。

#### 缓存级别分析

缓存命中率估算（假设 LRU 淘汰）：

对于随机访问 N 个键的集合，每次访问命中的概率 ≈ min(1, Pool / TreePages)：

| Scale | 总页数（约） | 池大小 | 估计缓存命中率 | IOPS |
|:-----:|:-----------:|:------:|:--------------:|:----:|
| 1,000 | ~5 | 64 | ~100% | ~1,018,574 |
| 10,000 | ~42 | 64 | ~100%（池 > 总页） | ~73,789 |
| 100,000 | ~400 | 64 | ~16% | ~16,448 |
| 500,000 | ~2,000 | 64 | ~3.2% | ~12,564 |
| 1,000,000 | ~4,000 | 64 | ~1.6% | ~8,226 |

关键观察：当 10K 时总页数（~42）仍然小于池（64），但 IOPS 却从 100 万降到了 7.4 万。
这意味着除了缓存命中率，还有其他因素起作用——

**更深层原因**：随机查找时，即使 42 页能全部放进 64 页的池，但 1 万次随机分布在 42 页上，
每次访问切换到不同页的 LRU 行为导致：访问 A → A 被移到 LRU 尾部 → 之后再次访问 A 时如果
中间访问了其他页，A 可能已经被移到 LRU 头部 → 甚至被淘汰 → 需要从磁盘重新加载。

在 1K 规模（4 页）时这不成问题——4 页完全在池中且频繁命中。在 10K 时 42 页虽能全放入，
但每页被访问的频率不够高，LRU 链上的位置不断变动。

### 4.7 多角度分析

#### 吞吐量角度

| Scale | IOPS | 每次操作耗时 | 相对 1K 的衰减 |
|:-----:|:----:|:-----------:|:--------------:|
| 1,000 | 1,018,574 | ~0.98 μs | 1.0× |
| 10,000 | 73,789 | ~13.6 μs | 13.8× |
| 100,000 | 16,448 | ~60.8 μs | 61.9× |
| 500,000 | 12,564 | ~79.6 μs | 81.1× |
| 1,000,000 | 8,226 | ~121.6 μs | 123.8× |

数据每扩大 10 倍，吞吐量大约降一个数量级，显示 LTM 场景下可扩展性主要受 I/O 瓶颈约束。

#### 可扩展性角度

按操作次数归一化：第 1K 行在 1000 次操作上测，第 1M 行在 1000000 次上测。
后者测量窗口更大，统计更稳定。

从 1K 到 1M（1000 倍数据增长），吞吐量下降约 124 倍。
这比"理想情况"（树高从 1 到 3 = 3 倍页访问）差得多，说明缓存竞争随规模非线性放大。

#### 冷热缓存对比

| Scale | Run0（冷） | Run1+（热） | 热/冷比 |
|:-----:|:----------:|:-----------:|:--------:|
| 1,000 | 906,125 | 1,074,798 | 1.19× |
| 10,000 | 68,414 | 76,477 | 1.12× |
| 100,000 | 16,797 | 16,274 | 0.97×（基本持平） |
| 500,000 | 12,984 | 12,143 | 0.94× |
| 1,000,000 | 6,038 | 10,414 | **1.72×** |

有趣的是，100K~500K 规模下冷热差距很小。这是因为建树过程本身已经在缓存中填充了大量页面，
Run0 的"冷"只是相对更冷。而 1M 规模下 Run0 特低、Run1 反弹，可能是因为建 1M 树后缓存
中充满了大量旧页，Run0 时随机访问的这些页面很多已经被淘汰，但 Run1 时利用 Run0 建立的
缓存状态，命中率提升。

#### 方差角度

- **小规模（1K）**：CV=9.5%，方差大 — 微秒级测量受 OS 调度噪声影响
- **中等规模（10K~500K）**：CV=3.4%~6.9%，方差正常 — 稳定 I/O 主导
- **大规模（1M）- Run0 vs Run1**：Run0=6038, Run1=10414，差异 72% — 不是因为测量噪声，而是因为两次运行的实际缓存状态不同

### 4.8 核心结论

1. **数据量每扩大 10 倍，吞吐量约降为 1/10** —— 这是 LTM 场景的基本规律
2. **树高从 1 到 3（3 倍页访问）只能解释 3 倍性能差异**，其余来自缓存竞争
3. **池大小固定时，纯查找性能由"有效工作集大小 ÷ 池大小"决定**
4. **小规模测量值不可靠（CV ≈ 10%）**，大规模测量（CV ≈ 3-5%）更可信

### 5.6 多层级分析

#### 页面级分析

每次 `FetchPage` 调用触发：

1. 查 page_table_（哈希表，O(1)）
2. **命中**：pin_count++，从 LRU 链表移除 → O(1)
3. **未命中**：FindVictim → 刷脏页（如有）→ 读磁盘 → 加入 page_table_ → O(n) LRU 扫描

在 Pool=4 的情况下，每访问一个新页面就要淘汰一个旧页面，每次 FetchPage 都需要：
- 被淘汰页面如果脏 → 写磁盘（4KB）
- 新页面从磁盘加载（4KB）
- 两次 4KB I/O

所以在 thrashing 状态下，一次 FetchPage 可能触发 8KB 的 I/O 流量。

#### 缓存级别分析

**LRU 链长度**与淘汰效率：

| PoolSize | 可容纳页数 | 与工作集关系 | LRU 扫描效率 |
|:--------:|:----------:|:------------:|:------------:|
| 4 | 4 | 远小于 200 | 每次 miss 扫描 4 帧，很快找到 victim |
| 64 | 64 | 工作集的 32% | 开始吸收热点 |
| 128 | 128 | 工作集的 64% | 临界区 |
| 256 | 256 | 超过 200 | 全命中 |

**关键洞察**：Pool=64 时吞吐从 ~2.8 万提升到 ~3.8 万（+36%），Pool=128 时继续提升到 ~6 万
（+59% vs Pool=64），但真正的 jump 在 Pool=256 时，吞吐跳到 ~82 万（+1262% vs Pool=64）。

这意味着 64 和 128 虽然不能完全容纳工作集，但通过吸收部分热点能带来线性增益。
当 Pool ≥ 工作集时，增益是指数级的。

#### 算法级分析

**为什么 Pool=128 的方差最大（CV=15.8%）？**

Pool=128 时，池刚好能装工作集的 64%。在随机访问模式下，某些运行时路径恰好遇到"热页面集"
（最近访问的 128 页大多是下一轮会命中的），而另一些路径则不幸（新页面刚好淘汰了即将访问的页面）。

这是典型的**缓存临界行为**：在阈值附近，系统的性能变得高度不稳定，微小的访问顺序变化
就能导致巨大的吞吐差异。

### 5.7 多角度分析

#### 吞吐量角度

```
Pool=4~32: ~27,000 IOPS (基线 thrashing)
Pool=64:   ~38,000 IOPS (+36%)
Pool=128:  ~60,000 IOPS (+122% vs Pool=4)
Pool=256:  ~822,000 IOPS (+2945% vs Pool=4)
```

Pool 从 4 提升到 32（8 倍），吞吐几乎不变。Pool 从 32 到 256（8 倍），吞吐提升 29 倍。
**这表明缓存容量存在明显的阈值效应**：小于阈值时加大池收效甚微，跨越阈值后收益爆发。

#### 存储效率角度

每页缓存对吞吐的边际贡献：

| 区间 | 新增缓存页数 | IOPS 增长 | 每页边际增益 |
|:----:|:-----------:|:---------:|:-----------:|
| 4→8 | +4 | +928 | ~232 IOPS/页 |
| 8→16 | +8 | +1,090 | ~136 IOPS/页 |
| 16→32 | +16 | -938 | 负收益（噪声） |
| 32→64 | +32 | +10,315 | **~322 IOPS/页** |
| 64→128 | +64 | +21,944 | **~343 IOPS/页** |
| 128→256 | +128 | +761,520 | **~5,949 IOPS/页** |

在 thrashing 区域，增加缓存几乎没有效果。一旦跨过阈值，每页的边际贡献呈指数级增长。

#### 冷热启动对比

三次重复运行之间，缓存初始状态不同：
- Run0：刚建完树，存有 200 页的数据（但全是顺序写入的初始状态）
- Run1：基于 Run0 结束时的缓存状态（已经有随机访问的痕迹）
- Run2：类似

结果各次之间差异小于统计噪声，说明缓存压力测试中初始状态差异不大，
主要瓶颈是持续的淘汰/加载循环。

### 5.8 核心结论

1. **缓存悬崖真实存在且极为陡峭**：Pool=128→256 时吞吐量跳升 12 倍
2. **临界区方差巨大**（CV=15.8%）：阈值附近性能不可预测
3. **低于阈值时增加缓存几乎无用**：Pool=4→32 时吞吐几乎没有变化
4. **LTM 场景设计准则**：必须保证池大小 ≥ 工作集，否则硬件投资浪费

## 6. 基准测试 3：树高演化 (`tree_height_evolution.csv`)

### 6.1 测试目标

验证 B+ 树高度随数据量增长的理论模型，并与实测值对比。

### 6.2 测试方法

### 6.6 多层级分析

#### 节点级分析

B+ 树的分裂时机：

**从 Height=1 到 Height=2（第 251 次插入）：**

根叶子节点满 250 个槽位后，第 251 次插入触发分裂：
```
[leaf: 250 entries] → [leaf1: 125 entries] + [leaf2: 125 entries] + [new root]
```

新根节点 `is_leaf_ = false`，`array_[0]` 指向 leaf1，`array_[1]` 指向 leaf2。

**从 Height=2 到 Height=3（约第 62,501 次插入）：**

当叶子节点继续分裂，内部节点（根）也满 250 个槽位时，再次分裂：
```
[root: 250 children] → [internal1: 125 children] + [internal2: 125 children] + [new root]
```

#### 树级别分析

**分裂次数估算**：

每次插入最多触发从叶子到根的一连串分裂（但实际很少，因为每个节点可容纳 250 个 key）。

- 插入 100 条：0 次分裂（未满）
- 插入 500 条：1 次分裂（根满 → 新根+2 叶子）
- 插入 50K 条：约 200 次叶子分裂 + 1 次根分裂
- 插入 1M 条：约 4000 次叶子分裂 + 250 次内部节点分裂 + 0~1 次根分裂

**扇出的意义**：250 的扇出意味着树的高度增长极慢。二叉树在 100 万条数据时高度 ≈ 20，
B+ 树高度 = 3。这直接决定了 I/O 次数：20 次 vs 3 次。

#### 理论 vs 实测对比

实测与理论完全匹配，说明：

1. 分裂算法实现正确
2. 扇出确实达到 250（没有因页内碎片而降低）
3. 根节点确实在满 250 个槽位时发起分裂

### 6.7 多角度分析

#### 可扩展性角度

| 数据量级 | 树高 | I/O 次数 | 可扩展性 |
|:--------:|:----:|:--------:|:--------:|
| 1~250 | 1 | 1 | 完全内存 |
| 251~62,500 | 2 | 2 | 2 次 I/O |
| 62,501~15.6M | 3 | 3 | 3 次 I/O |
| 15.6M~3.9B | 4 | 4 | 4 次 I/O |

在十亿级数据量下，B+ 树只需 4 次 I/O。这是 B+ 树成为数据库索引首选的根本原因。

#### 与替代方案对比

| 数据结构 | 1M 条时的查找代价 | 每次 I/O 的页数 |
|---------|:----------------:|:--------------:|
| B+ 树（扇出 250） | 3 次 FetchPage | 3 页 |
| 二叉搜索树 | 20 次 FetchPage | 20 页 |
| 哈希索引 | 1~2 次 FetchPage | 1~2 页（但无范围查询） |
| 跳表 | ~20 次 FetchPage | 20 页 |

### 6.8 核心结论

1. **理论模型完全精确**：实测高度与 log₂₅₀(N)+1 完全匹配
2. **百万级数据只需 3 次 I/O**，对比二叉树 20 次
3. **高度增长极慢**：从 0 到 100 万记录，高度只增加了 2
4. **扇出是影响树高的唯一因素**，增大扇出能直接减少 I/O 次数

### 7.6 多层级分析

#### 页面级分析

**顺序访问的页面访问模式：**

叶子节点在磁盘上是按 key 顺序分配的（插入顺序随着 key 递增，页 ID 单调递增），
因此顺序扫描时：

```
访问 key=1 → Load Leaf1（Page 1）
访问 key=2 → Leaf1 命中（缓存）
...
访问 key=250 → Leaf1 仍在缓存
访问 key=251 → Load Leaf2（Page 2）
```

在 Pool=32 的情况下，最多同时缓存 32 个叶子页。顺序扫描时每次只前进一个叶子页，
每页被连续访问 250 次后才跳到下一页。这意味着 32 页的池完全足以缓存全部 active 的叶子。

**随机访问的页面访问模式：**

```
访问 key=42 → Load Leaf1 → 后来 unpin，加入 LRU
访问 key=873 → Load Leaf4 → 后来 unpin，加入 LRU
...
访问 key=101 → 可能是 Leaf1 → 如果 Leaf1 还没被淘汰 → 命中
                也可能是 Leaf1 已被淘汰 → 重载
```

随机访问破坏了时间局部性。由于 LRU 只保留最近使用的页面，而随机访问的"最近"和"下一次"
之间可能隔了数百次其他访问，导致有效缓存命中率极低。

#### 树级别分析

顺序访问时，B+ 树的内部节点在遍历过程中被频繁访问（每次 GetValue 都从根开始）。
但由于所有内部节点加起来只有几十页（树高 2-3），它们全部常驻在 32 页的池中。

随机访问时，内部节点同样常驻，但叶子节点的访问模式完全不同，导致 32 页的池中
大部分被叶子页占用，且不断翻转。

#### 缓存级别分析

**顺序访问的有效工作集**：在任意时间窗口内，叶子扫描的工作集 ≈ 2-3 页（当前正在读的页 + 下一页）。
32 页的池绰绰有余。因此顺序访问的 IOPS 稳定在 ~70 万，且几乎不随数据规模下降。

**随机访问的有效工作集**：几乎等于整棵树的叶子页数（40~4000 页），远超 32 页的池。
因此绝大部分访问需要从磁盘加载。

**顺序/随机倍率随规模扩大的原因：**

| DataSize | 顺序 IOPS | 随机 IOPS | 比率 | 树总叶子页数 |
|:--------:|:---------:|:---------:|:----:|:-----------:|
| 10,000 | 676,523 | 38,108 | **17.8×** | ~40 |
| 50,000 | 765,901 | 26,287 | **29.1×** | ~200 |
| 100,000 | 767,486 | 18,514 | **41.5×** | ~400 |
| 500,000 | 748,597 | 11,395 | **65.7×** | ~2,000 |
| 1,000,000 | 702,222 | 10,228 | **68.6×** | ~4,000 |

比率从 18 倍增长到 69 倍。原因：顺序访问的吞吐量几乎不随规模下降（始终 ~700K IOPS），
而随机访问的吞吐量持续下降（因为叶子页增多 → 缓存命中下降）。

#### 50K 数据的异常

50K 顺序访问的 Run0=508K 明显低于 Run1=896K 和 Run2=893K。

原因：Run0 时缓存处于"冷"状态——建树过程中的页面访问模式与顺序扫描不同，
建树时可能有些叶子页已被驱逐或 LRU 位置不利。Run0 的顺序扫描将大量叶子页重新加载
到缓存中，使得 Run1 和 Run2 的缓存状态大幅改善，性能提升 76%。

这从另一个角度说明：**顺序扫描可以作为缓存预热手段。**

### 7.7 多角度分析

#### 吞吐量角度

顺序访问稳定维持在 ~70 万 IOPS，波动范围 68 万~80 万（CV < 5%，排除 Run0 冷启动）。
随机访问从 3.8 万（10K）降到 1 万（1M），下降约 3.7 倍。

#### 访问模式对比

| 维度 | 顺序 | 随机 |
|------|:----:|:----:|
| IOPS（1M 规模） | ~702,222 | ~10,228 |
| 可扩展性 | 几乎不受规模影响 | 随规模增大而下降 |
| 缓存依赖 | 极低（只需要 2-3 页） | 极高（需要整棵树的叶子） |
| 瓶颈 | CPU（内存拷贝+二分查找） | I/O（磁盘读取） |

#### 方差角度

顺序访问 CV 普遍 < 5%（50K 异常除外），说明缓存状态稳定。
随机访问 CV 偏大（4-13%），因为随机数生成器的种子不同 → 访问顺序不同 → 缓存命中率不同。

### 7.8 核心结论

1. **顺序访问快 18~69 倍**，差距随数据规模扩大而扩大
2. **顺序访问的性能不随数据规模下降**（始终 ~70 万 IOPS），因为有效工作集很小
3. **顺序扫描可以预热缓存**（50K 数据 Run0 到 Run1 提升 76%）
4. **随机访问的性能由缓存命中率决定**，命中率 ≈ min(1, Pool / LeafPages)
5. 设计提示：**B+ 树的叶子节点链式结构使范围查询极为高效**

## 8. 基准测试 5：写放大分析 (`write_amplification.csv`)

### 8.1 测试目标

量化页式存储系统的写放大效应——小更新在物理 I/O 层面的代价放大。

### 8.2 测试方法

- 预分配 10 个页面
- 每次逻辑更新（修改某页的部分字节）后，强制触发该脏页的淘汰
- 每次淘汰写回整页（4096 字节）
- WAF = 总物理写入字节数 / 总逻辑更新字节数

### 8.3 CSV 格式

| 列 | 类型 | 说明 |
|----|------|------|
| UpdateSize | int | 每次逻辑更新的字节数 |
| WAF | double | Write Amplification Factor |

### 8.4 完整数据

| UpdateSize | WAF | 物理/逻辑比 | 有效利用率 | 每 1 万次更新写入量 |
|:----------:|:---:|:-----------:|:----------:|:------------------:|
| 8 | 512.0× | 写 4096B / 改 8B | 0.2% | ~40 MB |
| 64 | 64.0× | 写 4096B / 改 64B | 1.6% | ~40 MB |
| 256 | 16.0× | 写 4096B / 改 256B | 6.3% | ~40 MB |
| 1,024 | 4.0× | 写 4096B / 改 1024B | 25% | ~40 MB |
| 2,048 | 2.0× | 写 4096B / 改 2048B | 50% | ~40 MB |

注：每万次更新的总物理写入量始终为 10000 × 4096 = ~40MB，因为每次淘汰都写一整页。

### 8.5 图表

![WAF Analysis](../data/waf_analysis.png)

绿色虚线为 SSD 典型阈值（2×），橙色为 HDD 典型阈值（5×）。

### 8.6 多层级分析

#### 页面级分析

页式存储的基本困境：**存储设备（SSD/HDD）的最小写入单位是页（4KB），
但应用程序的最小修改单位可能是字节。** 二者之间的差距就是 WAF。

在本测试中，每次逻辑更新后立即强制淘汰该页，所以 WAF 严格等于 PAGE_SIZE / UpdateSize：

```
WAF = 4096 / UpdateSize
8B:   4096/8 = 512
64B:  4096/64 = 64
256B: 4096/256 = 16
1KB:  4096/1024 = 4
2KB:  4096/2048 = 2
```

#### 系统级分析

**真实场景下的 WAF 更低**：本测试是"最坏情况"——每次更新后立即刷出。在实际数据库中：

1. 多个更新可能命中同一页（脏页合并），一次写回覆盖多次修改
2. buffer pool 会延迟写回（等到淘汰时才写），有机会合并脏页
3. B+ 树的内部节点更新频次低于叶子节点

**但 B+ 树引入了额外的 WAF 来源**：

1. **节点分裂**：每次分裂需要写 2 个新页 + 更新父节点
2. **索引与数据分离**：B+ 树只存索引，数据存其他地方（本实现 KV 合一，不适用）
3. **WAL（Write-Ahead Log）**：如果需要事务支持，日志也有 WAF

#### SSD 寿命影响

以更新粒度 8B（WAF=512）为例：

| 指标 | 计算 | 含义 |
|------|------|------|
| 每次逻辑更新物理写入 | 4KB | 实际写入 |
| 1 亿次更新总写入 | 100M × 4KB = 400GB | 物理写入量 |
| SSD 典型寿命（256GB） | 256GB × 3000 P/E = 750TBW | 总可写入量 |
| 可支撑的 8B 更新次数 | 750TB / 4KB = 1.88 亿次 | ~1.9 亿次 |
| 如果将 WAF 降到 2 | 750TB / 8KB = 938 亿次 | 提高 256 倍 |

所以 WAF 对 SSD 寿命的影响极大——从 512 倍降到 2 倍可使 SSD 寿命延长 256 倍。

### 8.7 多角度分析

#### 更新粒度角度

WAF 随更新粒度线性下降（对数坐标）。将更新粒度从 8B 提升到 64B（8 倍），
WAF 从 512 降到 64（8 倍）。改进是完全线性的。

#### 硬件角度

| 存储设备 | 典型 WAF 容忍度 | 安全更新粒度 |
|---------|:--------------:|:-----------:|
| 企业级 SSD | ≤ 2×（设备级 WAF 已考虑） | ≥ 2KB |
| 消费级 SSD | ≤ 10× | ≥ 400B |
| HDD | ≤ 50× | ≥ 80B |
| 本测试（8B 更新） | 512× | 远超所有设备承受范围 |

#### 优化角度

降低 WAF 的常见技术：

| 技术 | 效果 | 代价 |
|------|------|------|
| 增大更新粒度（批量合并） | 线性降低 WAF | 延迟增加 |
| 增大页大小（如 16KB） | 每页可合并更多小更新 | 更大的读放大 |
| 使用 delta 存储 | 只记录变更不写整页 | 读时需要合并 |
| 使用 COW（Copy-on-Write） | 避免原地更新 | 空间放大 |
| 写入合并（write coalescing） | 同页写入合并 | 需要合并层 |

### 8.8 核心结论

1. **小更新的 WAF 极高**（8B 更新 → 512×），是 SSD 寿命杀手
2. **WAF = 4096 / UpdateSize**（在本测试的极端条件下），是严格线性关系
3. **实际系统中的 WAF 低于本测试**（页合并、延迟写）
4. **设计准则**：应用层尽量合并小更新，利用脏页合并机制
5. **硬件选择**：LTM 场景应优先考虑低 WAF 的存储设备

### 9.6 多层级分析

#### 页面级分析

混合负载比纯查找更复杂：

- **查找**：与纯查找相同，从根到叶子遍历（读路径）
- **插入**：从根到叶子遍历 → 插入 → 可能触发分裂（写路径）
- **更新**：从根到叶子遍历 → 重写叶子槽位（写路径）

插入操作可能触发节点分裂，产生额外的页面写入（2~3 页/次分裂）。

#### 树级别分析

**树总页数随操作增长**：混合负载从 Scale/2 条预填开始，执行过程中不断插入新 key
（30% 比例），最终树中的记录数 ≈ Scale/2 + Scale×30% = 0.8×Scale。

| Scale | 最终记录数 | 树总页数（约） | 树高 |
|:-----:|:----------:|:--------------:|:----:|
| 10,000 | ~8,000 | ~32 | 2 |
| 50,000 | ~40,000 | ~160 | 2 |
| 100,000 | ~80,000 | ~320 | **3** |
| 500,000 | ~400,000 | ~1,600 | 3 |
| 1,000,000 | ~800,000 | ~3,200 | 3 |

在 100K 处树高从 2 跳到 3（因为 8 万条记录 > 62,500 的 2 层容量上限）。

#### 缓存级别分析

**10K 异常高值（723,243 IOPS）的原因**：

10K 规模下，树总页数仅 ~32 页，64 页的池完全容纳。而且混合负载的操作有 50% 是查找，
这些查找访问的是树中已有的 key（位于树的"已预热"部分）。更重要的点是：

10K 规模下的操作类型分布：
- 插入（30%）：新 key 插入，每次需要定位叶子页 → 如果叶子页在缓存中，速度很快
- 查找（50%）：已有 key 的查找 → 全缓存命中
- 更新（20%）：已有 key 的更新 → 同样全缓存命中

在大规模下，树页数超过池，操作中的随机访问部分（查找的 50% + 更新的 20%）
大量触发淘汰/加载，而插入 30% 则需要更新叶子页（写）并可能触发分裂。

### 9.7 多角度分析

#### 吞吐量角度

| Scale | Mixed_IOPS | 纯查找 IOPS（同规模） | 混合/纯查找比 |
|:-----:|:----------:|:-------------------:|:-------------:|
| 10,000 | 723,243 | ~73,789（随机） | ~9.8× |
| 100,000 | 39,340 | ~16,448（随机） | ~2.4× |
| 1,000,000 | 18,218 | ~8,226（随机） | ~2.2× |

注意 10K 时混合负载远快于纯查找随机访问——这是因为混合负载中有顺序插入（预先分配的 key 范围）
和更新的局部性，而纯查找是完全随机。在大规模下，混合负载约快 2.2 倍，
主要是因为操作中有 30% 是插入（新 key 的写入有更好的局部性）。

#### 操作分解角度

假设各操作的耗时：
- 查找 = 1 单位
- 更新 ≈ 1 单位（需要写，但页可能在缓存中）
- 插入 ≈ 1~5 单位（可能触发分裂）

30% 插入 + 50% 查找 + 20% 更新的加权代价远低于纯随机查找（100% cache miss），
因为插入操作在"未满的叶子页"上通常命中缓存。

### 9.8 核心结论

1. **混合负载吞吐量在 1.8 万~72 万 IOPS 之间**，取决于数据规模
2. **10K 时极高（72 万）**：全缓存 + 操作混合的优势
3. **大规模时下降到 ~1.8 万**：缓存竞争成为主要瓶颈（树页数 > 池）
4. **混合负载比纯随机查找快 2.2~9.8 倍**，因为写入操作有更好的局部性
5. 设计启示：**只读和读写混合场景的性能特征不同，需要针对性优化**

### 10.6 多层级分析

#### 页面级分析

**当 Workset ≤ Pool 时：**

所有页面常驻内存，访问模式为轮询（sequentially cycling），因此：
- 首次访问某页 → FetchPage 命中缓存，返回内存指针
- 后续访问 → 始终命中（页一直在池中），没有 I/O

这是纯内存操作的吞吐量：~300 万 IOPS。

**当 Workset > Pool 时：**

以 Workset=20, Pool=10 为例：
```
访问页 A → 加载到池 → 池满（10/10）
访问页 B → 需要淘汰 A → 加载 B → A 被驱逐
访问页 C → 需要淘汰 B → 加载 C → B 被驱逐
...
一轮循环后：再次访问页 A → A 已被驱逐 → 重新从磁盘加载
```

每轮循环中，10 个页面被淘汰、10 个页面被重新加载。每个页面在两次访问之间
经历了恰好 20 次其他页面访问，因此 LRU 链上的位置不断前移直到被驱逐。

#### 缓存级别分析

**阈值效应**：

| Workset/Pool 比 | 状态 | 平均 IOPS |
|:---------------:|:----:|:---------:|
| 5/10 = 0.5 | 全命中 | ~2,235,241 |
| **10/10 = 1.0** | **全命中（刚好）** | **~3,033,694** |
| **20/10 = 2.0** | **完全发散** | **~19,971** |
| 50/10 = 5 | 严重发散 | ~27,135 |
| 100/10 = 10 | 严重发散 | ~21,616 |
| 500/10 = 50 | 严重发散 | ~17,012 |
| 1000/10 = 100 | 极严重发散 | ~13,472 |

**悬崖比 = 3,033,694 / 19,971 ≈ 152×**。

#### 工作集/池比率分析

| 比率 | 性能 | 特征 |
|:----:|:----:|------|
| ≤1 | ~300 万 IOPS | 纯内存，极快 |
| 2~5 | ~2 万 IOPS | 持续淘汰，性能下降 150× |
| 10~50 | ~1.7~2.7 万 IOPS | 淘汰率饱和，略微波动 |
| 100 | ~1.3 万 IOPS | 最大工作集，LRU 链最长 |

值得注意的是：Workset=20 时（2 倍于池）的吞吐量比 Workset=1000 时（100 倍于池）只慢不到 2 倍。
这说明一旦工作集超过池大小，**增加工作集只会带来边际恶化**——瓶颈已经是 I/O 带宽，
更多的页面只是让 LRU 扫描链变长，但 I/O 次数已经达到上限。

### 10.7 多角度分析

#### 吞吐量角度

**悬崖边缘的精确位置**：Workset=10（/=10）时 IOPS=3,033,694 → 全命中。
Workset=20（2×pool）时 IOPS=19,971 → 几乎全 miss。

差别就是 1 页——如果工作集是 11 页：
- 每轮循环：第 1~10 页在池中，第 11 页迫使第 1 页被淘汰
- 下一轮访问第 1 页时：重新加载
- 结果：每轮有一个页面需要重载，IOPS 介于全命中和全 miss 之间

#### 方差角度

这是一个方差分析的极好案例：

| Workset | CV | 解释 |
|:-------:|:--:|------|
| 5 | **40.8%** | 全缓存时测量在微秒级完成，OS 调度噪声相对巨大 |
| 10 | **2.4%** | 稳定的全命中，测量时间窗口较长（1 万次操作） |
| 20 | **12.7%** | 临界状态，淘汰/命中的随机波动 |
| 50 | **2.1%** | 稳定的 thrashing，I/O 主导 |
| 100 | **10.6%** | LRU 扫描链长度的影响 |
| 500 | **28.9%** | 大工作集下，LRU 扫描链的不确定性 |
| 1,000 | **34.0%** | 最大工作集，初始条件不同导致结果分散 |

**有趣的反直觉现象**：全命中和全 miss 的反而是低方差，中间状态方差高。
这与"信号传输"中的概念类似——在确定性状态（全命中或全 miss）下系统行为可预测，
在临界状态（正好在悬崖边缘）下系统行为变得高度随机。

#### 硬件角度

按 IOPS 估算等效硬件：

- **300 万 IOPS**：相当于中端 NVMe SSD 的随机读取能力（~500K-1M IOPS）的数倍，
  说明这是纯内存操作（DRAM 延迟 ~100ns，3M IOPS ≈ 333ns/op，近似 L3 缓存速度）
- **2 万 IOPS**：相当于 SATA SSD 或低端 NVMe 的水平，说明 I/O 成为瓶颈

### 10.8 核心结论

1. **缓存悬崖在 152 倍**（工作集=10 页 → 20 页），这是本测试中最陡峭的性能悬崖
2. **全缓存时吞吐量 ~300 万 IOPS（纯内存）**，远高于所有其他测试的最大值
3. **全 miss 时吞吐量 ~2 万 IOPS（I/O 瓶颈）**，与缓存压力测试的 thrashing 基线一致
4. **跨过阈值后继续增大的工作集只带来边际恶化**，不是因为 I/O 少了，而是 I/O 已经饱和
5. **命中/临界/发散三种状态的方差特征完全不同**

## 11. 方差与重复测量分析

### 11.1 各基准测试的方差总览

| 测试 | 最小 CV | 最大 CV | 中位 CV | 高方差场景 |
|------|:-------:|:-------:|:-------:|-----------|
| 纯查找 | 3.4% | 37.6% | 6.9% | 1K（OS 噪声），1M（Run0 vs Run1 状态差） |
| 缓存压力 | 2.7% | 15.8% | 6.3% | Pool=128（临界区域） |
| 顺序 vs 随机 | 2.1% | 29.1% | 5.0% | 50K 顺序冷启动 |
| 工作集压力 | 2.1% | 40.8% | 12.7% | 全缓存（小工作集），大工作集 |

### 11.2 方差的系统学解读

通过方差我们可以推断系统内部状态：

#### 低方差场景（CV < 5%）

- 顺序访问（所有规模）
- 大规模随机访问
- 稳定 thrashing（Pool << 工作集）

这些场景的瓶颈稳定——要么是内存带宽，要么是磁盘 I/O 延迟。系统行为确定性强。

#### 中方差场景（CV 5-15%）

- 中等规模随机访问
- 缓存临界区
- OS 调度干扰

这些场景中缓存状态对访问顺序敏感，而访问顺序受随机种子影响。

#### 高方差场景（CV > 15%）

- 全缓存小工作集（微秒级测量受 OS 调度影响大）
- 缓存悬崖临界点
- 大规模冷热缓存状态差异

### 11.3 重复测量的价值

如果没有重复测量：

```
纯查找 1M 数据：只有 6,038 IOPS（Run0） → 结论：1M 时只有 6K 吞吐量
如果有重复测量：均值 8,226 IOPS（Run0+Run1） → 更准确
```

对于 1M 规模，Run0 和 Run1 的 72% 差异完全来自两次运行的缓存状态不同，而不是系统噪声。
单次测量会严重高估或低估实际性能。

### 11.4 方差与测量窗口的关系

| 测量窗口 | 典型方差 | 原因 |
|---------|:-------:|------|
| 微秒级（< 1ms） | 20-40% | OS 调度、CPU 缓存状态、分支预测 |
| 毫秒级（1-100ms） | 5-15% | 少量 I/O 操作的随机波动 |
| 秒级（> 1s） | 2-5% | 大数定律，I/O 时间稳定 |

## 12. 跨基准测试综合讨论

### 12.1 基准之间的交叉验证

通过不同测试的对比，可以交叉验证关键发现：

| 发现 | 证据 1 | 证据 2 | 一致性 |
|------|--------|--------|:-------:|
| 缓存悬崖 | 缓存压力：Pool=128→256 ↑12× | 工作集压力：10→20 页 ↓152× | ✅ |
| 随机访问缓存命中率低 | 纯查找：1M 时仅 8K IOPS | 顺序 vs 随机：差距 18~69 倍 | ✅ |
| 树高影响有限 | 纯查找：1K→10K ↑13.8×（树高从 1→2） | 10K→100K ↑4.5×（树高不变） | ✅ |
| I/O 瓶颈基线 | 缓存压力 thrashing：~27K IOPS | 工作集 thrashing：~20-27K IOPS | ✅ |
| 全缓存性能 | 工作集压力：~3M IOPS | 顺序访问：~700K IOPS（需查树） | 合理一致 |

### 12.2 缓存效率的统一模型

所有基准测试的缓存行为可以用统一模型解释：

```
有效吞吐量 = 缓存命中率 × 内存延迟 + (1 - 缓存命中率) × 磁盘延迟

其中：
  缓存命中率 ≈ min(1, Pool / 有效工作集)
  内存延迟 ≈ 0.1~1 μs（对应 1M~10M IOPS）
  磁盘延迟 ≈ 50~100 μs（对应 10K~20K IOPS）
```

代入典型值：
- 全命中：1 μs → 1,000,000 IOPS ✓（实际 ~3M，因为操作更简单）
- 全 miss：100 μs → 10,000 IOPS ✓（实际 ~20-27K）
- 50% 命中：50 μs → 20,000 IOPS

### 12.3 设计启示

#### 对于 LTM 场景的部署建议

1. **Pool 大小选择**：必须 ≥ 预期工作集大小，否则性能断崖式下跌
2. **数据分片**：如果总数据 1M 页，但工作集只有 10%，那么 Pool=1000 页就够了
3. **访问模式感知**：顺序访问工作量小，可以为随机访问预留更多缓存
4. **写合并**：小更新（< 256B）尽量合并，否则 WAF 极高

#### 对于 B+ 树实现的优化方向

| 问题 | 本实现 | 可能的优化 |
|------|--------|-----------|
| 随机访问缓存命中率低 | LRU 淘汰 | 预取（prefetch），分区缓存 |
| 写放大 | 页级回写 | 日志结构合并（LSM 风格） |
| 内部节点缓存浪费 | 页级缓存统一管理 | 内部节点固定缓存 |
| 冷启动慢 | 无预热机制 | 顺序扫描预热 |

#### 与 LSM-tree 的对比

| 维度 | B+ 树（本实现） | LSM-tree |
|------|:--------------:|:---------:|
| 随机读 | 1-3 次 I/O（树高） | 需要查多个层（O(log²N)） |
| 顺序读 | 极快（叶子链表） | 极快（有序 SSTable） |
| 写放大 | 高（小更新） | 更高（压缩写回），但可通过合并降低 |
| 读放大 | 低（精确查找） | 高（需查多个层） |
| 实现复杂度 | 中等 | 高（压缩策略、层数调优） |

### 12.4 性能瓶颈总结

```
内存带宽（~3M IOPS）
  ↑ 缓存命中率 < 100%
磁盘 I/O 带宽（~20K IOPS）
  ↑ 树高 > 1（+内部节点访问）
二分查找 CPU（节点内 O(log 250)）
```

在实际 LTM 场景中，瓶颈从"内存带宽"转移到"I/O 带宽"，约 15,000% 的性能下降。
任何优化都应聚焦于减少磁盘 I/O 次数和提升缓存命中率。

## 13. 数据质量与局限性

### 13.1 测量环境

本测试在以下环境中完成：

| 项目 | 说明 |
|------|------|
| 操作系统 | Windows 11 |
| 编译器 | GCC (MSYS2 UCRT64) -O2 |
| 存储设备 | NVMe SSD |
| 内存 | ≥ 2 GB |
| CPU | x86-64 |

### 13.2 已知局限

1. **冷启动效应**：每次测试新建数据库文件，文件系统缓存为空。连续运行测试时，
   前面的测试可能影响后面的文件系统缓存状态

2. **BS 大规模测试的 Run 数**：500K 和 1M 规模只做了 2 次重复（而非 3 次），
   统计代表性不足

3. **单次测量**：混合负载和写放大只有单次测量，无法计算方差

4. **微秒级测量的精度**：小规模测试（1K 规模）在微秒级完成，受 Windows 线程调度影响大

5. **文件系统缓存干扰**：操作系统本身也有文件缓存（Windows 的文件缓存可能导致
   某些磁盘读取实际命中在系统缓存中），使测量偏向于更好

6. **测试负载不真实**：纯随机访问不反映真实应用（真实负载有倾斜），
   工作集压力测试用轮询模式（过于规律）

### 13.3 数据可靠性

| 数据类型 | 可靠性 | 说明 |
|---------|:------:|------|
| 树高 | ★★★★★ | 确定性计算，不受环境噪声影响 |
| WAF | ★★★★☆ | 确定性计算（无重复），单次测量 |
| 大规模 IOPS | ★★★★☆ | 长时间窗口，稳定 I/O 主导 |
| 小规模 IOPS | ★★★☆☆ | 短时间窗口，OS 噪声影响大 |
| 混合负载 | ★★★☆☆ | 单次测量，无方差数据 |
| 临界缓存区 | ★★☆☆☆ | 高方差，结果对随机顺序敏感 |

## 14. 结论与设计启示

### 14.1 核心发现

**1. Larger-than-Memory 场景下，缓存命中率是唯一重要的性能指标**

IOPS 从全命中的 ~300 万降至全 miss 的 ~2 万，差距 150×。
树高的影响（从 1 到 3 层）只贡献了约 3 倍差异。

**2. B+ 树的高扇出使树高增长极慢**

百万级数据只需 3 层，理论可支持至 39 亿条（4 层）。
与二叉树相比 I/O 次数减少 85-90%。

**3. 顺序访问远快于随机访问（18-69 倍）**

且顺序访问的吞吐量不随数据规模下降。
缓存的局部性原理决定了这一差距。

**4. 页式存储的写放大是固有问题**

小更新（8B）的 WAF 高达 512×，但可以通过写合并有效降低。
应用层应避免频繁的原地小更新。

**5. 重复测量揭示系统行为**

高方差区间（临界缓存区、小规模全缓存）的识别本身就是有价值的信息，
帮助理解系统在不同状态下的行为特征。

### 14.2 设计准则

| 准则 | 依据 | 量化指标 |
|------|------|---------|
| 池大小 ≥ 工作集 | 缓存悬崖效应 | 否则性能下降 150× |
| 优先保证随机访问的缓存 | 顺序访问不依赖缓存 | 混合/纯差 18-69 倍 |
| 合并小更新 | 写放大 | 8B→512×, 2KB→2× |
| 避免缓存临界区 | 临界方差高 | CV=15-41% |
| 大规模采用多次测量 | 缓存状态影响大 | Run0/Run1 差可达 72% |

### 14.3 扩展方向

- **多线程并发**：在 BufferPool 层加 latche，BPlusTree 层用 crabbing 协议支持并发
- **预取**：识别顺序访问模式，提前加载下一叶子页
- **缓存分区**：固定缓存内部节点，防止被叶子页淘汰
- **自适应替换**：使用 ARC（Adaptive Replacement Cache）替代纯 LRU
- **批量写**：合并多个小更新后再回写，降低 WAF
- **NUMA 感知**：在多 socket 系统中将池分配到本地内存
